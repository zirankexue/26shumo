## 联合 ALNS：有可用思想，但必须换评价内核

`q3.py:463–469` 把 `joint_cost` 传入 `q2.alns`，因此它确实在改变运输方案，不能把它描述成“固定 Q2 后只加中继”。但 `q2.py:453` 调用 `initial_solution()`，不是直接使用 `q3.py:435–440` 读取的 Q2 方案热启动；Q2 在这里主要用于基准统计和目标归一化。三随机种子 `[1,7,23]` 也共享逐服务区、重箱优先、C 型优先的初始构造，再通过随机操作产生差异。

可以借鉴的五类销毁为随机箱、Shaw 空间/质量相关箱、高代价箱、整架次、整服务区；一次随机销毁约 6–16 箱。当前两架次邻域难以跨越需要同时重组三架次以上才显益的结构，可增加“同一中继窗口服务的若干架次”和“晚返航/电池瓶颈附近若干架次”的销毁，再从当前真实可行候选做 CP 修复。这里的中继相关性应来自当前连续证书，不采用旧检查点分类。

旧修复代码也有不应复制的细节：`try_insert()` 在新建架次时先按代价选择某机型，但输出阶段 `q2.py:199–206` 又重新选第一个可行机型，代理代价与返回结构可能不一致；新服务区主要追加到尾部而没有完整枚举插入位置。`repair_regret()` 是“新建架次与当前最佳插入代价差”的简化 regret，不能当作标准前 k 个插入选择的 regret-k。其权重更新也只是简单加分与衰减。建议复用邻域概念，不移植这些实现细节。

优先实测方案：先把旧 20 架次完整结构和其它已验证方案的候选合并，保持原候选在池中；在相同冻结目标、相同硬约束和可比求解预算下运行紧凑 CP。若收益不足，再引入适量三架次大邻域。不要以旧 70.624574 kWh 或 9319.320822 s 与当前指标直接比较，因为几何、逐箱交付和同步约束口径不同。

## 时间聚类：当前推荐的三站均无可省空档

旧 `plan_relays()` 的 `max_per_station_span=3600` 实际比较的是**相邻需求点时间差**，不是整个聚类跨度。因此一串点的相邻间隔都小于一小时，整个中继任务仍可能远长于一小时。贪心站点选择只最大化覆盖点数，没有评估从第一个到最后一个点间的悬停代价、返航代价和实体冲突。

对当前冻结推荐 JSON 的 `relay=True` 连续证书按实际时刻求并集，结果为：

| 中继站 | 连续认证需求并集（s） | 最大空档（s） | 在 Cmax 不变时，增加一次中继架次的分裂盈亏平衡空档（s） |
|---|---:|---:|---:|
| H0720 | [725.400339, 1503.398006] | 0 | 3786.577 |
| H0020 | [1918.781281, 3600.811721] | 0 | 4239.075 |
| H0003 | [2976.675022, 6144.650786] | 0 | 3957.721 |

冻结评分中增加 1 架次的惩罚相当于约 **0.967919954 kWh** 的能耗；表中还计入额外往返与建链能耗。推导为：

`cE = alpha_energy × 10^9 / span_energy`，`cN = alpha_sorties / span_sorties`，

`gap_break_even = (extra_travel_and_setup_energy + cN/cE) × 3600 / (P_hover+P_comm)`。

这只是保持其它目标和资源安排不变时的候选筛选，不是全局最优证明。如果新分组改变需求时间窗或能通过分裂显著降低 Cmax，则仍应交由 CP 评估。当前固定结构下三站需求已分别连续，直接复制时间聚类不会节省闲置悬停，因此它的优先级低于结构候选扩展和站点优化。

## 多站切换：可以扩展，但旧代码没有完成这个模型

旧代码对每个检查点维护可覆盖站列表，在 `q3.py:254–256` 用不同站贪心拿走需求点。这意味着同一运输架次的不同检查点可能由不同站负责，但代码没有给出前后检查点之间的覆盖区间、更没有证明切换瞬间无断链。`comm.py:61–130` 虽提供更密的爬升/巡航/下降采样函数，实际 `q3.py` 导入的是 `common.CommModel` 并调用自己的稀疏 `sortie_checkpoints()`；不能把未调用的更密采样函数算作运行路径的保障。

安全实现应把当前连续证书分解成一组有完整起止时刻的需求区间，给每段列出经过认证的可用站；选择后对各站要求 `service_start <= transport_start + first` 且 `service_end >= transport_start + last`，接入和回传同时成立。站间切换边界应由证书端点对齐或有交叠认证支持。根代理当前已在做 `requirements` 接口扩展，本审查不修改主求解器。

为了控制规模，建议先每架次最多 2 个固定后备站，只对单站不可覆盖或单站代价明显偏高的候选尝试两站组合，并保留全部原单站选项。这样改进解不会依赖弱化通信判定。若目标是同站多架次拆窗，需同时扩展站点任务槽、组件分配、300 s 周转与完整充电占用，不能只拆 CSV 行。

## 物理与 Notebook 不能直接移植

版本二运输公式中 `g=9.80665` 和载荷指数 `1.5` 与师兄口径相近，但不代表完整物理一致：`common.py:235–247` 用间距约 10 m 的双线性插值采样最大高程，LOS 也通过离散采样；`direct_ok/access_ok/backhaul_ok` 的路径损耗距离使用水平距离，没有计入高度差。当前模型的 DEM、航段完整 1 ms 取整、连续通信证书和逐箱交付必须保留。

Notebook 则有更根本的问题：

1. cell83 的地形由 16 个节点高程插值成 60×60 网格，cell85 直接拿该示意地形做通信判断，未读取原始 DEM。
2. cell85 最初的直连预算只用网关发射方向；cell86 仅按遮挡标记中继需求。cell114 虽修正了双向预算与遮挡下可通信分类，但用于灵敏度分析，没有重新构造并验证之前导出的联合方案。
3. cell90/91 的盲区窗口让爬升和下降时水平位置仍沿整条航线移动，且循环没有完整累计交接及返航阶段，不能替代真实三阶段轨迹。
4. cell92 初版中继排程随后被 **cell93** 覆盖；最终硬编码 `S003:[46.7,98.7]min` 与 `S012:[9.9,14.7]min`，`depart=w0-t_fly`、`arrive=depart+t_fly` 没有准备和建链时序，后续图表使用这个覆盖后的 `relay_sched`。

因此 Notebook 不能提供可复用的真实中继窗口、通信切换或最终能耗。只保留其概念流程与展示思路。

## 建议的实测顺序与接受条件

1. **现在就测：多来源完整运输结构候选＋当前物理过滤＋紧凑 CP。** 已交付 Deepseek 20 架次结构种子。旧候选留在池中，日志记录源方案、候选是否通过物理/通信过滤及拒绝原因。
2. **现在就测：需求定向的站点和高度加密。** 优先针对长窗口、晚返航、低通信裕量；沿用真实 DEM/链路，并将输入与候选源 hash 放入缓存键，避免旧版本二“只要缓存文件存在就加载”的问题。
3. **随后小规模测：两站连续切换选项。** 先验证证书拼接和实际到位，再评估 F，不得把离散检查点覆盖率作为可行性。
4. **有新空档再测：同站拆窗和中继组件复用。** 当前固定方案没有需求空档，盲目拆窗优先级低。新结构出现大空档或续航瓶颈时，再做完整任务槽与组件资源模型。
